# 0008. What 1.0 promises

Date: 2026-10-04. Status: accepted.

## Context

Until 1.0 a minor version may break anything, and UPGRADE.md lists what did. From 1.0
the version number has to mean something to people who never read the changelog:
`composer require ianfoxdev/outbox:^1.0` and `outbox-relay:1` must keep working across
every 1.x release.

Three things are versioned with one tag, and each has users who depend on different
parts of it: application code calls the PHP package, the relay reads the table the
package writes, and consumers read what the relay publishes. Some promises are not in
any signature. Two relays of different versions run side by side during a rolling
update; if they derive different lock keys from the same settings, both lead at once
and the order of events is gone. Kafka keys an aggregate to a partition; if a new relay
partitions differently, the events of one aggregate land in two partitions, and order
across the upgrade is gone too.

This ADR lists what is promised, so that a change to any of it is recognized as
breaking before it ships.

## Decision

From 1.0.0 the project follows semantic versioning strictly. A change to anything below
is a major version. A minor version adds; a patch version fixes.

**PHP package.** Every class, interface, trait and enum in `src/` that is not marked
`@internal`, with:

- public method names, parameter types, return types, and parameter names (PHP 8
  callers use named arguments, so `Message::json(aggregateId: ...)` is a call to keep
  working);
- public properties of `Message`, and its validation rules: a message accepted by 1.0
  is accepted by every 1.x;
- the exception classes, their hierarchy, and that every exception the package throws
  itself implements `OutboxException`. Errors of the application's own connection (a
  PDOException, a DBAL exception) pass through unchanged and are not part of it;
  `WriteFailed` is thrown only by `PdoConnection` when PDO is not in exception mode;
- interfaces that applications implement (`Connection`, `Recorder`, `ProducesEvents`)
  never gain a method in 1.x. Something new comes as a separate interface the package
  checks for with `instanceof`;
- Laravel: the config keys and their environment variables, the container bindings for
  `Outbox` and `Recorder`, the `outbox-config` and `outbox-migrations` publish tags.
  Symfony: the `outbox` config tree, the services `Outbox` and `Recorder`, the
  `outbox:migration` command and its options.

**The table.** The columns, their types and their meaning in `schema/postgresql.sql` and
`schema/mysql.sql`. A 1.x version may add a nullable column or an index, with an
UPGRADE note and a migration, only if a relay that does not know about it keeps
working, and a package that does not write it keeps working. Anything else is 2.0.

**The relay.**

- Environment variables, their defaults and their meaning. A new variable may come in a
  minor version with a default that keeps the old behavior.
- How the leader lock is identified: the key derived from `OUTBOX_TABLE` when
  `OUTBOX_LOCK_ID` is not set, and on MySQL the lock name `outbox-relay:<OUTBOX_LOCK_ID>`.
  Relays of any two 1.x versions with the same settings compete for the same lock.
- What a consumer receives. On Kafka: the record key, the value, the `ce_*` headers and
  `content-type`, the topic template, and the partitioning (murmur2 of the key, as the
  Java client does). On RabbitMQ: the message properties, the `cloudEvents_*` headers,
  the routing key template, persistence and `mandatory`. A 1.x version may add a header,
  never remove or change one.
- The order guarantee of ADR 0002 and ADR 0007, and at-least-once delivery.
- Metric names, types and labels. New metrics may come in a minor version.
- The HTTP endpoints `/healthz`, `/readyz` and `/metrics`, their status codes, and the
  `healthcheck` subcommand.
- The `msg` of the log lines the runbook relies on: `relay started`, `became leader`,
  `another replica is the leader, standing by`, `leader stopped`, `batch not fully
  published`, `publishing recovered`, `cleanup failed`, `relay failed`, and their
  attribute keys. Error texts inside them are not covered: they come from drivers and
  brokers.
- Image tags: `X.Y.Z`, `X.Y` and, from 1.0, `X` for the latest of a major version.
  `latest` follows the newest stable release, never a release candidate.

**Not covered:** anything marked `@internal`; service ids that start with `outbox.`; the
Go packages of the relay (they are `internal/` and cannot be imported); the text of
`/readyz` answers; the examples, the test code, the soak and load test commands; the
Kubernetes manifests and the compose files, which are examples to adapt.

**Supported versions.** Dropping a PHP, framework, database or broker version that has
reached its end of life is not a breaking change and comes in a minor version: Composer
and the requirements table keep older installations on the release that still
supports them.

**Deprecation.** Something that will go away in 2.0 is marked `@deprecated` in a minor
version, with the replacement named in the docblock and in UPGRADE.md, and keeps
working until 2.0.

**After 2.0.** The last 1.x minor version gets security fixes for six months after 2.0
is released.

## Rejected

**Promise the PHP API only.** The relay and the table break installations as surely as
a renamed method, and nobody would see it coming: a lock key derived differently would
pass every test of a single version.

**Make `Connection` and `Recorder` final-by-convention, free to grow.** Applications
implement both; a new method breaks them with a fatal error at deploy time. A second
interface checked with `instanceof` costs one class.

**Remove the dialect shortcuts of `Schema` before 1.0.** `postgresql()`, `mysql()` and
their `Statements` variants duplicate `sql()` and `statements()`. Keeping them costs
nothing to maintain; removing them breaks code for no gain.
